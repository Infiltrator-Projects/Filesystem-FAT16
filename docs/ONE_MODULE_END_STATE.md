# FAT16: one module, complete filesystem, universal consumers

**Authoritative end state:** one independently distributed `FAT16.so` is the **entire FAT16 filesystem driver** and single source of filesystem semantics. The module lives under `/System/Filesystems/FAT16.so` and is discovered by BOOT, the InfiltratorOS kernel and all applications through reviewed, versioned module interfaces and generic loader/host adapters. See [the cross-project authority](https://github.com/Infiltrator-Projects/Filesystems/blob/main/docs/UNIFIED_FILESYSTEM_MODULE_ARCHITECTURE.md).

The end user must **not** have to manage `fat16.ko` and `FAT16.efi` as two additional filesystem products. The preferred engineering result is one source implementation reused across all execution environments. Internal executable representations and bridges are acceptable only where proven necessary; they must not fork FAT16 parsing, write/format/recovery logic into three separately maintained engines.

- **BOOT:** the BOOT-owned loader eventually executes or adapts the appropriate trusted functionality **from the same FAT16.so file** and supplies bounded UEFI block I/O and boot-file services. A conventional Linux userspace ELF cannot be passed directly to firmware `LoadImage`; a controlled module profile, verified payload or other proven universal loader is required. BOOT's default boot-path operations remain read-only.
- **Kernel:** the eventual kernel-owned generic module loader or filesystem bridge consumes the same FAT16 implementation. Stock Linux still uses VFS/kernel-safe drivers or an appropriate userspace filesystem service; any interim `fat16.ko` is an implementation bridge, not a separate future filesystem product. Early-root availability, kernel ABI and signing are requirements.
- **Filesystems, Defragmenter, Test Media, Disks, Files and Setup:** consume FAT16.so's format operations; generic I/O, privilege and safety adapters remain generic. Independent external image tools validate changes so the engine cannot certify itself.

**Present state versus destination:** Earlier releases and the current repository source include independent Linux kernel and EDK2/EFI implementations and tests. They are transitional engineering evidence; the universal BOOT/OS loading of one `.so` is **not yet implemented, tested or released**. Release notes, built artifacts and licensing remain factually accurate, but three shipped binaries must never be advertised as the finished one-file objective.

**Migration gates:** prove one trusted complete read/write/format/rename/delete/recovery ABI; prove Defragmenter calls this very module; implement BOOT loading and real OVMF/kernel-image access from the same file; implement a kernel bridge for mount/read/write/remount/root bootstrap; verify host ABI, secure boot, staging a byte-identical module on firmware-readable media, rollback, and physical test media before calling FAT16 complete. Do not delete functional `.ko`/`.efi` paths until replacements pass independent equivalence tests.
